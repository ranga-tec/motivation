## 2. Architecture

```text
Browser ──HTTPS 443──► Caddy ──┬─ /api/*, /auth/*, /health ─► api (ASP.NET Core 8, :8080)
          (HTTP 80 →    (TLS,  │                                   │
           redirect)   gzip)   └─ everything else ──────────► frontend (React build on nginx, :8080)
                                                                   │
                                                      database (PostgreSQL 17, :5432)
```

All four containers run from `POMS/deploy/contabo/compose.yaml` under the Compose project name
`poms`. Only Caddy publishes ports. The API and database are reachable only inside the private
Docker network.

| Container | Image | Purpose |
| --- | --- | --- |
| `poms-caddy-1` | `caddy:2.8-alpine` | HTTPS (automatic Let's Encrypt), routing, compression, HSTS |
| `poms-frontend-1` | built from `POMS/frontend/Dockerfile` | React single-page app served by unprivileged nginx |
| `poms-api-1` | built from `POMS/src/Poms.Api/Dockerfile` | REST API `/api/v1`, Identity sign-in `/auth`, health |
| `poms-database-1` | `postgres:17-alpine` | Application data, users and roles |

### Persistent data (Docker volumes)

| Volume | Mounted at | Holds | Lose it and… |
| --- | --- | --- | --- |
| `poms_database` | `/var/lib/postgresql/data` | All patients, records, users | all data is gone |
| `poms_files` | `/app/storage` (api) | Patient photos and uploaded documents | uploads are gone |
| `poms_keys` | `/home/app/.aspnet/DataProtection-Keys` (api) | Sign-in token keys | everyone must sign in again |
| `poms_caddy_data` | `/data` (caddy) | HTTPS certificates | Caddy re-issues them automatically |
| `poms_caddy_config` | `/config` (caddy) | Caddy runtime state | nothing important |

Uploaded files are stored on the server disk; no object storage is used or needed.

### Files in `POMS/deploy/contabo`

| File | Purpose |
| --- | --- |
| `compose.yaml` | The four-container stack |
| `Caddyfile` | HTTPS site, routing rules, HTTP/1.1 + HTTP/2 only |
| `.env.example` | Template for `.env` |
| `setup-server.sh` | One-time server preparation and first start |
| `backup.sh` | Database dump + uploaded-files archive, 14-day retention |

### Environment variables (`.env`)

| Variable | Meaning |
| --- | --- |
| `POMS_DOMAIN` | Public host name. Drives the HTTPS certificate, CORS origin and the frontend API URL. |
| `POSTGRES_PASSWORD` | Database password. Generated by `setup-server.sh`. Letters and digits only. |
| `BOOTSTRAP_ADMIN_EMAIL` | First administrator, created only when the database has no users. |
| `BOOTSTRAP_ADMIN_PASSWORD` | Its password (12+ chars, upper, lower, digit, symbol). |

The API also receives fixed values from `compose.yaml`: `ASPNETCORE_ENVIRONMENT=Production`,
`DATABASE_URL=...?sslmode=disable` (private network, no TLS needed), `FileStorage__RootPath`,
`Cors__AllowedOrigins__0=https://$POMS_DOMAIN` and `SeedDemoUsers=false`. Demonstration accounts
such as `admin@poms.lk` never exist on this server.

## 3. Access

```bash
ssh root@169.58.173.191
```

Root login uses SSH keys. To give another workstation access, append its public key to
`/root/.ssh/authorized_keys`. If SSH is broken, use the Contabo customer panel → VNC console.

Firewall (`ufw`): only `22/tcp` (SSH), `80/tcp` and `443/tcp` are open.

## 4. First installation (already done 2026-10-14)

```bash
ssh root@169.58.173.191
git clone https://github.com/ranga-tec/motivation.git /opt/poms
cd /opt/poms/POMS/deploy/contabo
bash setup-server.sh   # installs Docker + ufw, creates .env with a database password, then stops
nano .env              # set BOOTSTRAP_ADMIN_EMAIL and BOOTSTRAP_ADMIN_PASSWORD
bash setup-server.sh   # installs the nightly backup cron job, builds and starts the stack
```

The bootstrap administrator is created only on an empty database. After that, staff accounts are
managed in the application under **Administration → Users & access**.

## 5. Day-to-day operations

### Deploy the latest code

```bash
cd /opt/poms
git checkout -- POMS/deploy/contabo/backup.sh   # discard the chmod made by setup-server.sh, if shown
git pull
cd POMS/deploy/contabo
docker compose up -d --build
```

The build takes 3–6 minutes. The site stays available while images build; containers restart in
a few seconds at the end. Database schema changes are applied automatically when the API starts.

### Status and logs

```bash
cd /opt/poms/POMS/deploy/contabo
docker compose ps                         # all four should be "Up"; database "(healthy)"
docker compose logs -f api                # API log (Ctrl+C to stop)
docker compose logs --tail 100 caddy      # certificate and proxy log
curl -s https://169-58-173-191.sslip.io/health
```

### Restart

```bash
docker compose restart api        # one container
docker compose up -d              # recreate anything stopped
```

The containers use `restart: unless-stopped`, so they start again after a server reboot.

### Operating-system updates

```bash
apt-get update && apt-get upgrade -y
reboot     # only when the upgrade asks for it; POMS comes back by itself
```

## 6. Backups and restore

Two independent layers:

1. **Contabo Auto Backup** — daily snapshot of the whole server, last 10 versions, restored from
   the Contabo customer panel.
2. **POMS nightly backup** — `/etc/cron.d/poms-backup` runs `backup.sh` at 02:30 server time:
   - `/var/backups/poms/db_<date>.dump` — PostgreSQL custom-format dump
   - `/var/backups/poms/files_<date>.tar.gz` — all uploaded photos and documents
   - files older than 14 days are deleted; output is logged to `/var/log/poms-backup.log`.

Run a backup on demand:

```bash
bash /opt/poms/POMS/deploy/contabo/backup.sh
```

Both layers live with the same provider. For protection against losing the Contabo account or
data centre, periodically copy `/var/backups/poms` off the server, for example:

```bash
scp -r root@169.58.173.191:/var/backups/poms ./poms-backups
```

### Restore

```bash
cd /opt/poms/POMS/deploy/contabo
docker compose stop api
docker compose exec -T database pg_restore -U poms -d poms --clean --if-exists < /var/backups/poms/db_<stamp>.dump
docker run --rm -v poms_files:/files -v /var/backups/poms:/backup alpine \
  sh -c "cd /files && tar xzf /backup/files_<stamp>.tar.gz"
docker compose start api
```

## 7. Security notes

- HTTPS only; HTTP redirects to HTTPS and responses carry HSTS.
- Public self-registration is disabled (`POST /auth/register` returns 404).
- The API limits each user or IP to 120 requests per minute; real client IPs come from Caddy's
  `X-Forwarded-For` header.
- The database is not exposed outside Docker.
- `.env` is mode 600. Never commit it or paste its contents into tickets or chat.
- Restricted clinical records are visible only to their author and staff granted
  "Restricted clinical data".

## 8. Moving to an organisation domain

1. In the domain's DNS, create an `A` record (for example `poms.exceedlanka.org`) → `169.58.173.191`.
2. Wait until `nslookup poms.exceedlanka.org` returns that IP.
3. On the server, set `POMS_DOMAIN=poms.exceedlanka.org` in `.env`.
4. Run `docker compose up -d --build`. The frontend is rebuilt with the new address and Caddy
   requests a certificate for it.
5. Users must use the new address; the sslip.io name stops working once `POMS_DOMAIN` changes.

## 9. Troubleshooting

| Symptom | Cause and fix |
| --- | --- |
| Blank page, console shows `ERR_QUIC_PROTOCOL_ERROR` | Browser cached the old HTTP/3 offer. HTTP/3 is now disabled in the `Caddyfile`; open a private window or restart the browser. |
| `502` from `/api` or `/health` | API container not running. `docker compose logs --tail 50 api`. |
| API log: `SSL connection requested` | `DATABASE_URL` lost `?sslmode=disable`. Restore `compose.yaml` from git. |
| `git pull` refuses: local changes to `backup.sh` | `git checkout -- POMS/deploy/contabo/backup.sh`, then pull again. |
| Certificate errors | `docker compose logs caddy`. Ports 80 and 443 must be open and `POMS_DOMAIN` must resolve to the server. |
| Forgotten administrator password | Another administrator resets it under Users & access. If none exists, restore access from a backup or recreate the account directly in the database. |
| Disk filling up | `df -h /`; prune old images with `docker image prune -f`; check `/var/backups/poms`. |
